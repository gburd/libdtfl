# libdtfl: correctness and verification steering

Use this before claiming any change works.

## Where bugs in a dataflow port hide

The ways a port can produce wrong answers while every test stays green:

1. **Progress tracking that is almost right.**  A frontier that advances
   one step too early still produces correct output most of the time.
   Wrong output shows up only when a message is in flight at the
   moment of the early advance.  Single-threaded tests almost never
   create that moment.  Tests run under the simulation allocator (PLAN
   D8) do.
2. **Compaction that loses a distinction.**  `advance_by` and
   consolidation errors leave every *current* answer correct and break
   only queries at older times, or only after a later merge.  Model
   tests must query at many times, not just the latest.
3. **Merges that drop or double updates.**  Spine merges are fueled,
   so a merge can be half finished when a cursor is taken.  The
   property tests interleave exert, insert, compaction and cursor
   reads.
4. **Order-dependent code in a supposedly deterministic path.**
   Channel IDs depend on all workers building dataflows in the same
   order.  Anything iterating a hash table in a construction path can
   break that.
5. **Refcount and capability leaks.**  Rust frees these automatically.
   In C, a leaked capability holds a frontier back forever, so the
   dataflow hangs instead of crashing.  The debug-build leak check at
   worker shutdown names the operator.

## Oracles, strongest first

1. **The naive model** (`tests/model/`).  Recompute the collection from
   scratch at each time and compare.  The model implements the
   accumulation semantics from `formal/Differential/Compositional.lean`
   at the differential pin.  Cite the theorem in the test.
2. **The pinned Rust program.**  For examples and interop, run the Rust
   program at the pin with the same inputs and compare the outputs.
   Fixtures are generated by `dev/gen-fixtures` and committed.
3. **Upstream's own oracles**: the sequential BFS and SCC, and
   `ReferenceTactic` for reduce.
4. **A hand-computed expected value.**  Acceptable for unit tests of
   small pieces only.

A test that compares the C code with itself (for example, two libdtfl
code paths that share a helper) is not an oracle.

## Evidence rules

- Record what produced a result: the commit, the configure flags, the
  compiler and the allocator.  For anything under the simulator,
  record the seed too.
- A fix that cannot be shown to fail before the change is unverified.
  Say so.
- "Probably a race" or "probably variance" is not a diagnosis.  Get a
  seed or a sanitizer report.
- When a run fails, keep its log before rerunning.  A later pass does
  not explain an earlier failure.
- In status reports, name each verification tier as run, skipped
  (with the reason), or not attempted.
