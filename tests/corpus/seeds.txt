## notify_multiworker: Counter drops a flush (fixed, c2e9f74)
#
# Property: tests/pbt/pbt_ops_notify.c notify_multiworker.
# Found by: make check-sim with DTFL_PBT_FLUSH_STEPS=on, hegel 0.36.5.
# Minimal case: 2 simulated workers, seed 0, no faults; worker 0 sends
# one record at epoch 1, flushes, steps once, closes.  The run never
# completed and stopped at the simulator's step cap.
# Cause: the pinned timely Counter forwards a flush only while its
# produced batch is undrained (dev/upstream-notes.md, "Counter drops a
# flush once its produced count is drained").  Reproduces on real
# threads (DTFL_PBT_COMM=process hung) and in Rust at timely 0.31.0 and
# on timely master; reported upstream as timely-dataflow issue #824.
# State: fixed in c2e9f74, a deliberate divergence (ADR-0012,
# 2026-10-23): the Counter also forwards a flush when it pushed data
# since the last one.  The flush draw is now on by default, so check-sim
# covers it.  Expected now: REPLAY PASS.  Checked both ways: REPLAY FAIL
# ("simulation made no progress after 2000001 steps") before c2e9f74,
# REPLAY PASS after.
notify_multiworker DTFL_PBT_FLUSH_STEPS=on DTFL_PBT_COMM=sim DTFL_PBT_FAULTS=on DTFL_PBT_ONLY=notify_multiworker DTFL_PBT_REPLAY=AXiczcoxCgAACAJAbewd/f+NCU1B1JqDh2BAcapYoGHLGuF9eUUC8LABtw== tests/pbt/pbt_ops_notify
